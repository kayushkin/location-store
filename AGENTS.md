# About location-store

## What it owns

`:8333`, loopback only. Where the user has been: named places (`place_000001`), visits to them (`visit_000001`), trips between them (`trip_000001`), the raw location points underneath (millions possible, no public ids, read by time) and the imports that brought them in (`import_000001`). Place, visit and trip ids are registered in kanban-store's entity-type registry as types `place`, `visit` and `trip`, so a journal-store timeline item or a note cites a particular drive or trip as a chip. **Location history is private**: a front door such as dash adds the auth this service has none of, and nothing here is copied to noteboard. `CONTRACT.md` is the route table.

# How it works

## Imports and what they never touch

`location-import-google -file <file or directory>` reads Google's on-device Timeline export (`Timeline.json`), legacy Takeout `Records.json`, and legacy Semantic Location History month files, told apart by their top-level keys (`internal/googletimeline`). `location-import-photos` makes each photo-store photo with GPS and a trusted date (`exif`, `filename` and `google_photos` by default) into a point with source `photo` and `source_ref` the photo id. `location-import-activity` makes each activity-store activity whose coordinates Google measured on the device (Locations basis `From your device`; a saved home or work address or a guess from past activity is left out) into a point with source `google_activity` and `source_ref` the activity id; activity-store has no coordinates filter, so it reads every activity (about a minute). `location-import-photo-sidecars -dir <dir>` reads every `sidecars.jsonl` under the directory (Google Takeout photo sidecars, one per line, keyed by the photo file's sha256), finds each photo in photo-store by `GET /photos?sha256=`, and makes a photo with sidecar `geoData`, no GPS of its own and a trusted date into a point with source `google_photos_sidecar`, `source_ref` the photo id and time the photo's `taken_at`. All four go through `internal/importclient`: `POST /imports` with the file's sha256 (a finished hash is a no-op, an unfinished one resumes), `POST /imports/{id}/batches` of 2000 records in one transaction each, `POST /imports/{id}/finish`. Records are found again by key: a place by `google_place_id`, a visit or trip by `source` + `source_ref` (`<started_at>-<ended_at>`), a point by time, coordinates and source. **An import never touches** a name, title, description, tags or `parent_trip_id`, never changes a place link already set, never changes a `mode` someone corrected (one that no longer matches `ModeForGoogleActivityType(source_mode)`), and leaves a record someone deleted deleted. Every update, import change, delete and restore of a place, visit or trip first copies the whole record to `revisions`. An on-device Timeline export is a full snapshot of its span: the importer sends its span and raw-position range with `POST /imports/{id}/finish`, the store records which visits and trips each file holds (`import_records`), and of the snapshots covering a record's start the newest (by newest raw position, then oldest raw position, then import order) decides whether it stands; one it does not hold is soft-deleted with `superseded_by_import_id`, unless someone edited it. `-reapply` sends a file again, for imports made before the store kept what each file holds. CONTRACT.md *Snapshots* has the rule. Visits inside other visits (`hierarchyLevel` above 0), `timelineMemory` and the iPhone export (a top-level array) are not read. Which files and machines this host's history came from is not in this repo: see the noteboard note tagged `location-store`.

## Localities, home periods and journeys

`location-name-localities` downloads GeoNames' public `cities1000` dump once to `<data dir>/geonames` (the data dir comes from the service's `GET /settings`), then calls `POST /localities/fill`, which names the town of every empty `locality` inside the service (`internal/geonames`): no coordinate ever goes to an outside service, and none may — no Nominatim, no Google API. `location-group-journeys` calls `POST /journeys/group`, whose decisions are all in `journeys.go`: nights at 03:00 local, home periods from a 21-night rolling majority (`home_periods`, ids `home_period_000001`), journeys as spans more than 80 km from home or with a flight, made into trips of kind `journey`, source `generated`, with the movements attached. Who wrote a generated value is on the record (`title_by`, `parent_set_by`, a locality's `described_by`), and a run rewrites only its own: a title or parent set through the routes is `hand` and stays. Journeys made by hand (`POST /trips`, kind `journey` by default) are never touched. There is deliberately no level above journeys yet; home periods are the likely seed of one.

`location-match-calendar` reads Google Calendar events through dash (`DASH_URL`, `DASH_TOKEN`; the service never holds the token) and sends them to `POST /calendar/match`, whose decisions are all in `calendar.go`: `calendar_event_links` (`calendar_event_link_000001`) tie an event, by Google's calendar and event ids, to a visit, a flight or a journey. Locations are matched offline, against place names and addresses in the store and GeoNames town names; a recurring routine never links by time alone. A recurring series with no location links where the user arrives for most of its times out (`unlocated_series_place`), and what each series came to is kept in `calendar_series_places` (`GET /calendar-series-places`), linked or not. A run rewrites only links whose `matched_by` is its own; one a person deleted stays deleted. There is no import pipeline script: run the imports (`location-import-google`, `location-import-photos`, `location-import-activity`, `location-import-photo-sidecars`) → `location-name-localities` → `location-group-journeys` → `location-match-calendar` → `location-suggest-place-names`, in that order. CONTRACT.md *Calendar events* has the rules.

## Place name suggestions

`location-suggest-place-names` reads OpenStreetMap extracts on disk (`LOCATION_STORE_OSM_EXTRACTS`, default every `.osm.pbf` in `~/.cache/osm`; Geofabrik's regional files, one per region) with `github.com/paulmach/osm/osmpbf` (`internal/osmextract`), and the calendar through dash, and sends what lies near each unnamed place (`GET /unnamed-places`) to `POST /place-suggestions/proposals`, where `place_suggestions.go` decides. Calendar addresses are found by matching the street line against OSM `addr:*`, offline. Suggestions stay `proposed` until a person or agent accepts one (`POST /place-suggestions/{id}/accept` with `decided_by`), which names the place; a run never names, never renames, and never touches a decided suggestion. No coordinate or address may go to an online geocoder. CONTRACT.md *Place name suggestions* has the rules.

# Working in this repo

## Build, test and deploy

Module `github.com/kayushkin/location-store`, root package `locationstore`, server `cmd/location-store`, importers `cmd/location-import-google`, `cmd/location-import-photos`, `cmd/location-import-activity` and `cmd/location-import-photo-sidecars`, and `cmd/location-name-localities`, `cmd/location-group-journeys`, `cmd/location-match-calendar` and `cmd/location-suggest-place-names`, thin clients of the routes that decide. No build tags. `go.mod` replaces `../llm-bridge` (settings), `../photo-store` (the photo importers read `photostore.Photo`) and `../activity-store` (the activity importer reads `activitystore.Activity`). Every variable it reads is declared once in `settings.go` with llm-bridge `servicesettings`, served at `GET /settings`; `TestEveryEnvironmentVariableTheServiceReadsIsDeclared` fails on an undeclared `os.Getenv`. `./deploy.sh` runs the shared deploy gate, tests, checks the running unit's environment, installs `location-store` and the eight commands to `~/bin`, restarts the user unit and fails unless `/health` is ok and the port is bound to loopback only. `./generate-ts.sh` renders `location.go` and `vocabulary.go` to `ts/model.ts`, published source-only as `@kayushkin/location-store-types` (`file:../location-store/ts`); bridge-ui's place, visit and trip chips read it.

## Public repository: nothing personal

This repo is public. Nothing about the user's own data goes in it — not in code, tests, comments, commit messages or this prompt: no real coordinates or addresses, no names of places the user goes, no machine names, file paths of their exports, account names, home directories or tokens. Tests use invented data on a grid near 10°N 20°E with made-up place ids (`example-home`) and made-up towns (`writeTownFixture`). A fact an agent here needs about this host's data goes in a noteboard note tagged `location-store`.
